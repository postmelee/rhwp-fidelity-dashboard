# Dashboard preview

The five views support direct links. Use `#overview`, `#renderers`, `#documents`, `#history` or `#methods`. Link to one immutable attempt with `#run-<run_id>-<attempt>`, or use `#compare-…` and `#document-…` to open its results directly. The navigation supports Left, Right, Home and End. With JavaScript disabled it works as an ordinary section index.

The PR Checks workflow builds a downloadable `dashboard-preview` artifact from the existing public numeric ledger at `17e6e4463c950c988c93b3ddb1afa09d8e556634`. Extract it, then run `python3 -m http.server 8001 --directory /path/to/extracted-preview` and open `http://127.0.0.1:8001/`. The preview uses `python3 scripts/build_preview.py --ledger PATH --out preview`. The production site still uses `scripts/pipeline.py build`, so the review build can land ahead of its public rollout. The preview and its tests have no measurement or Pages job.

The ledger stays authoritative for scores and measurement outcome. `scripts/site/evidence.json` records separately audited Actions jobs for particular attempts and an observed release tag/SHA. Pages status applies to the listed job, and an unaudited job remains unknown. The release check is dated; a later build can show a matching ledger record by SHA. The approved four documents form a smoke corpus.

## Scheduler and Pages follow-ups

- **Release order.** Scheduled selection takes the oldest unseen identity after sorting stable releases by publication time; a main push takes the newest stable release. Run [44694231379](https://github.com/postmelee/rhwp-fidelity-dashboard/actions/runs/44694231379) selected v0.7.10, and its producer failed the checkout contract. The existing ledger snapshot contains no v0.9.1 result. A separate scheduler change could select the newest unseen stable release first, then drain the prior backlog and retain bounded retries. Test a new release alongside older unseen releases and use a separately defined compatibility outcome only when the pinned checkout has explicitly failed the probe; infer nothing from tag age.
- **Pages lookup.** In the same run, artifact upload returned ID `14610525313` and the REST preflight found it. The [publish job](https://github.com/postmelee/rhwp-fidelity-dashboard/actions/runs/44694231379/job/136147672220) then logged an internal listing of two artifacts and found zero with the expected name. [The pinned deploy action](https://github.com/actions/deploy-pages/blob/d6db90164ac5ed86f2b6aed7e0febac5b3c0c03e/src/internal/api-client.js) uses the internal artifact service and matches by name. A REST success therefore leaves that lookup unverified. It is unclear why the two views differed. Validate the official pinned Pages upload/deploy pair in an isolated workflow first. If the lookup issue recurs, test a trusted build-and-deploy job with bounded retries for artifact lookup only, without rerunning measurement or overwriting records. Verify the exact live output after a separately approved production rollout.
